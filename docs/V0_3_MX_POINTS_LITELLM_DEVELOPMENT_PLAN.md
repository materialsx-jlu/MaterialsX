## 1. 产品边界与已确认决策

MaterialsX 0.3 让已登录用户在桌面端充值通用 MX 点数，并在研究任务中使用四条平台模型路由，按实际用量扣点。

| 决策 | 0.3 规则 |
| --- | --- |
| 上游采购 | 第三方供应商；不假设直接向 OpenAI 或 Anthropic 采购 |
| 模型入口 | `gpt-5.6-sol`、`gpt-6-sol`、`claude-opus-5-5`、`claude-fable-5-1` 四个产品槽位 |

## 3. 目标架构与责任

```text
用户桌面 Electron/Vue
  → MaterialsX Go API/模型网关（身份、准入、MX 点预留/结算、审计）
  → 内网 LiteLLM Proxy（四条固定模型别名、协议适配、采购用量观测）
  → 第三方供应商 API

微信支付 → MaterialsX 订单/验签/查单 Worker → PostgreSQL MX 钱包
计费人员 https://<billing-admin-host>/ → 独立计费 Web 进程 → 私有 Go 计费管理 API
                                                       → MaterialsX PostgreSQL 订单/钱包/用量/审计
平台运维 /ops → Go 路由发布服务 → LiteLLM 配置/密钥引用与四路探针
代理维护 内网 LiteLLM /ui → LiteLLM 专用 PostgreSQL（模型诊断、虚拟 Key、代理花费日志）
```

- **桌面端**：显示公开目录、每百万 Token 或每万 Token MX 点费率、充值面额、可用/预留/已用点数和任务账单；只发送 MaterialsX 登录凭据与用户选择的公开模型槽位。
- **Go 控制面**：服务端确认模型槽位、用户余额、任务预算、路由/价格版本和单次最大输出；先在事务中预留，再向 LiteLLM 发请求；仅凭可靠终态 usage 结算，释放余款。中断但上游是否计费未知时保持待核对。
- **LiteLLM**：只允许 Go 网关访问；映射四个别名到经验证的供应商 Base URL、上游模型 ID 和服务端 Key；限制可用路由、请求体大小和并发；回传实际模型、用量与请求关联 ID。供应商 Key 与代理管理 Key 不返回桌面。
- **PostgreSQL**：MaterialsX 数据库保存资金与 MX 点账本、价格/汇率/路由版本和审计；LiteLLM 若启用虚拟 Key、管理 UI 或 spend 日志，使用单独数据库和权限，不能成为用户账本真源。
- **独立计费 Web**：独立进程负责静态页面、同源 `/api/*` 反向代理和健康检查；工作人员查询用户、钱包、充值订单、消费与退款，处理对账异常、查看收入/成本/毛利，审批计价版本。资金规则和权限仍由 Go 执行。
- **运营 `/ops`**：沿用现有后台做部署、路由探针、服务暂停、发布与客服；计费入口链接到独立后台，不复制账本写逻辑。LiteLLM 自带管理 UI 仅供内网代理诊断，不作为普通用户页面。

### 3.1 三个部署单元及接口

| 部署单元 | 源码与独立产物 | 私有运行目录、监听与依赖 | 发布责任 |
| --- | --- | --- | --- |
| MaterialsX Go 业务服务（含现有 `/ops`、支付/结算 Worker） | `services/control-plane/`；Go 服务与 Worker 产物 | 现有业务运行目录和业务 PostgreSQL；对桌面提供业务 API，对计费 Web 提供受限管理 API | 单独版本、迁移、健康检查、日志和回滚；业务账本唯一写入方 |
| 用户计费 Web | `apps/billing-admin/`；独立 Vite 构建产物 `dist/billing-admin/` 与 Web 服务包 | `runtime/billing-admin/`；开发示例 `127.0.0.1:8790`，生产独立 HTTPS 主机；只代理私有 Go API，无数据库和供应商密钥 | 单独进程、配置、健康检查、部署与回滚；不嵌入 Go 的 `/ops` 静态资源 |
| LiteLLM Proxy | `services/litellm/`；锁定 Python 版本/依赖与配置模板 | `runtime/litellm/`；开发示例 `127.0.0.1:4000`，生产私网监听；独立 PostgreSQL 库/角色和供应商密钥 | 单独进程、配置快照、健康/四路探针、部署与回滚；只有 Go 网关调用 |

这三个单元可以先在同一台机器、同一个 Git 仓库，但**生产部署根目录不得共用**：建议分别使用 `/opt/materialsx-api/`、`/opt/materialsx-billing-admin/`、`/opt/materialsx-litellm/`，持久状态分别位于独立的 `/var/lib/materialsx-api/`、`/var/lib/materialsx-billing-admin/`、`/var/lib/materialsx-litellm/`，配置与密钥按服务账户分权。`runtime/*` 仅为本机开发目录约定，不能把整个仓库或共用 `runtime/` 作为生产发布包。三者必须分别安装、启动、停止、升级、回滚和查看日志；发布脚本不得一键覆盖另两个单元。Go 与计费 Web 的合同采用版本化管理 API；Go 与 LiteLLM 的合同固定别名、鉴权、usage 和请求关联 ID。任一方升级前做兼容性检查；需要跨服务变更时先部署兼容旧版的服务，再切换调用方，最后清理旧接口。计费 Web 故障不应中断已登录用户的桌面调用和扣点；LiteLLM 故障不应阻断计费后台查询账本，但模型调用应明确失败或进入待核，不得重复请求或扣点。

## 4. LiteLLM 无 Docker 目录部署

LiteLLM 是独立服务，不作为 Go 子进程、桌面安装包内容或计费 Web 的依赖启动。源码中只保留不含密钥的安装脚本、版本锁、配置模板和验收脚本；运行文件放入已被 Git 忽略的 `runtime/litellm/`。建议目录：

```text
services/litellm/                 # 可审查的安装/配置模板和验证脚本
runtime/litellm/.venv/           # 固定版本 Python 虚拟环境
runtime/litellm/config.yaml      # 从已发布路由快照生成；权限 0600
runtime/litellm/secrets.env      # 仅服务账户可读；四个上游 Key、代理 Key、数据库连接
runtime/litellm/logs/            # 脱敏运行日志；设定轮转和保留期
```

部署交付物须包括独立服务账户、进程管理配置（开发机 `launchd`，生产按目标系统选择）、私网监听地址、`/health/liveliness` 或锁定版本实测的健康端点、启动前配置校验、就绪后四路探针、日志轮转、备份与独立回滚脚本。生产反向代理仅允许授权运维访问 `/ui`，Go 到代理的流量走私网；计费 Web 和桌面不能直连代理。LiteLLM 的发布不重启 Go 或计费 Web；故障恢复后须用请求关联 ID 对齐待核用量，不能自动重放未知终态请求。

**本机数据库与代理现状（2026-10-07）**：本地 PostgreSQL `127.0.0.1:5432` 已创建 `materialsx_litellm` 数据库及同名专用登录角色，角色是该库 owner，非超级用户、无 `CREATEDB` 权限；已用专用账号验证连接。连接串、Master/Salt Key 和四个供应商 Key 仅在 Git 忽略的 `runtime/litellm/secrets.env`，目录权限 `0700`、文件权限 `0600`，不在本文记录口令。已固定 `litellm[proxy]==1.104.0`、Python 3.12 与完整依赖锁，完成专用库备份、迁移、Prisma 本机 Client 生成与 schema 索引补齐；本机 launchd 以独立进程监听 `127.0.0.1:4000`，`/health/liveliness`、`/health/readiness`、`/ui/` 和 `/v1/models` 已实测通过。当前只有三条诊断路由，`gpt-6-sol` 与销售仍关闭；Linux 独立服务账户、主机部署、管理 UI 实际登录权限、四路真实采购账单和完整协议探针尚需验收。生产环境另建专用库/角色，不能拿开发机库代替生产库。实施命令见 [0.3.1 独立服务运行手册](../services/litellm/README.md)。

部署脚本应做幂等的数据库/角色检查、备份与迁移预检；迁移账号只持有 LiteLLM 专用库所需权限。运行时 Go 业务库连接与 LiteLLM `DATABASE_URL` 分离，禁止 LiteLLM 账号访问 MaterialsX 用户、支付和 MX 点表。`LITELLM_SALT_KEY` 一旦加密保存上游凭据，须安全备份且不得随重启重新生成。

开发顺序：确认受支持 Python 版本 → 创建独立 venv → 安装并固定 `litellm[proxy]` 精确版本及依赖锁 → 离线检查版本和许可证清单 → 从模板生成四条路由 → 仅监听 `127.0.0.1` 或私有网卡 → 健康检查和四路合成探针 → 接入 `launchd`（macOS 开发机）及目标生产系统的进程管理器。启动、停止、重启、升级、回滚均提供仓库脚本；不能依赖某人的终端常驻。安装包只连接 MaterialsX 服务端，不在每位用户电脑上启动 LiteLLM。

四个槽位各有固定 LiteLLM 别名和独立的环境变量 Key。仓库提供 [四路配置模板](../services/litellm/config.example.yaml)，已填入 RootFlowAI OpenAI 兼容地址、四个上游模型 ID 和**标准档采购单价（每 Token）**；服务端私有环境需注入 `MX_SUPPLIER_GPT56_KEY`、`MX_SUPPLIER_GPT6_KEY`、`MX_SUPPLIER_OPUS55_KEY`、`MX_SUPPLIER_FABLE51_KEY`、`LITELLM_MASTER_KEY`、`LITELLM_SALT_KEY` 和专用 PostgreSQL 的 `DATABASE_URL`。模板无明文密钥；这些路由及协议仍须经过 Key 权限与真实响应探针才可发布。RootFlowAI 官方 [首个请求示例](https://rootflowai.com/docs/guide/first-request)证明 `/v1/chat/completions` 可使用 Claude 型号，但不自动证明这四个 Key 对应路由、Responses 或工具能力均可用。

LiteLLM 的自定义单价数字在其日志中会显示为 `$`，在本项目中仅作为 **RootFlowAI 站内额度/人民币采购成本的数值估计**，不能解释为真实美元，也不能拿其花费日志直接扣 MX 点。LiteLLM 的普通输入/输出/缓存价格只用于采购成本观测；**272,000 Token 长上下文档、缓存字段映射及实际扣额由 MaterialsX 第 5.3 节价格快照和供应商账单核对**。所用 LiteLLM 版本必须实测四类 Token 和长上下文价格；若其成本计算路径不匹配，标记成本估计不可用，MaterialsX 仍按可信 usage 与锁定零售价独立结算。

四路均做非流式、流式、工具往返、usage、429/5xx、断流、取消探针。若某路只能走 Chat Completions 而现有客户端使用 Responses，先完成明确的协议适配和用量验证，再开放该路。

LiteLLM 自带 Admin UI，默认由代理的 `/ui` 提供模型、虚拟 Key、用量和日志等内部管理入口；使用虚拟 Key、管理与花费记录时部署**独立 PostgreSQL 数据库**，并在锁定的无 Docker Python 安装上验收 `/ui` 静态资源、登录和权限。四条生产路由以仓库模板及 `/ops` 发布的配置快照为准，不在 LiteLLM UI 直接改价或改模型，防止双写漂移。即使启用 LiteLLM budget，MaterialsX 仍以自己的事务预留为资金准入条件，避免两套余额竞争。代理的 Master Key 仅供受限运维使用，Go 服务使用独立、只允许四模型的内部虚拟 Key；代理管理端口不对公网开放。日志默认脱敏，不记录科研原文、回答或供应商密钥。

## 5. MX 点钱包、价格与汇率

### 5.1 钱包与历史数据

新建 `mx-point` 单位与独立精度、余额聚合和不可变流水；**1 MX 点 = ¥0.10 的充值换算关系**，不等于任意固定数量的模型 Token。四款固定商品的金额由服务端按人民币分保存：1000/5000/10000/50000 分；到账点数为 100/500/1000/5000。客户端只提交商品版本 ID 和幂等键，不指定金额、点数或收款状态。

旧 `paid-credit` 账本、旧订单和已结算调用原样保留并单独显示。不得把旧 1000:1 联调积分直接改名成新 10:1 MX 点；若允许旧实付余额转换，需单独的不可变转换事件、按原支付价值核算、展示前后余额和审计，并在新钱包验收后执行。先确定旧开发联调账户的处理策略，不让它阻塞新账户的 0.3 功能开发。

内部使用整数最小单位或定点数，满足小额调用且避免浮点误差；付款金额始终以人民币分记录。一次调用附 `account_id`、任务/请求幂等键、模型槽位、上游路由版本、零售价版本、采购价版本、汇率版本及 usage 证据。跨批次预留与退款不能产生负余额。已消费部分的现金退款规则先以单独政策版本定义并经支付验收，不能复用旧整数试验规则。

### 5.2 采购价、汇率、零售价三层

| 层 | 数据 | 管理规则 |
| --- | --- | --- |
| 供应商采购价 | 币种、每百万 Token 的普通输入/输出/缓存读取/缓存创建、长上下文或额外收费项、起止时间、证据 | 记录供应商合同价或账单价；未知分类不能记为零 |
| 汇率 | `source_currency → CNY`、精确值、来源、采集时间、生效时间 | 管理员审核后发布快照；供应商人民币报价时倍率为 1；旧任务不随新汇率改价 |
| 用户零售价 | 每个公开模型每类 Token 的 MX 点单价、模型可用状态、生效时间、取整规则 | 后端发布不可变版本；用户调用前可见，运行中不改价 |

后台试算公式：`采购成本(CNY) = 用量 × 采购单价 × 生效汇率`；**0.3 首版直接加载第 5.3 节的固定售价**，不要求运营或开发再换算。后续改价可用官方折扣或目标模型毛利率生成候选，但**最终销售点价须由管理员发布**。实际扣点以发布的 MX 点价格版本及可靠 usage 为准，不在每次请求时读取波动汇率。LiteLLM 的 cost map 只作第二来源校验；供应商账单与 LiteLLM 估计不一致时保留差异并待核对，不反向改写用户历史账单。

发布前逐路确认输入/输出、缓存读写、推理 Token、工具调用及长上下文的供应商计费口径；无法可靠计量的收费项要么加入有上界的预留和价格模型，要么禁用相应能力。每次调用须有可信输入边界、最大输出和账户日/月/并发限额；超出用户已预留额度的供应商费用由平台承担并进入异常处理，不自动产生负点数。

### 6.2 登录、权限与 API

复用 MaterialsX 现有 `internal/identity` 管理员账户、密码策略和会话校验，不使用参考网站账号，不另建计费人员密码库。当前 `/ops` 会话 Cookie 的 `Path=/ops`；计费后台在**独立主机名**下使用不同 Cookie 名、host-only `Path=/` 的 HttpOnly/Secure/SameSite 会话 Cookie 与 CSRF/Origin 校验。生产环境强制 HTTPS；本机 HTTP 联调只允许回环地址并使用开发专属 Cookie 配置。两个后台共享身份主体，但会话不得跨主机名、后台角色或浏览器存储直接复用。生产环境按管理员 MFA 策略验收；本机关闭 TOTP 的联调配置不能自动成为生产策略。敏感操作需近期登录、服务器端角色检查、幂等键、版本号、原因和审计事件；列表/导出按最小权限脱敏。

首版角色：`billing.viewer`（查询和报表）、`billing.operator`（原单查单、退款预览及工单）、`billing.finance`（退款审批、账单导入与对账）、`billing.pricing`（价格草稿/审批）、`billing.admin`（员工授权与发布控制）。一名具名管理员可以先兼任多角色，但权限必须在 Go API 中逐项判定，不能只靠隐藏按钮。任意手工赠送/扣减 MX 点不作为首版通用按钮；若后续确有补偿需求，必须是专门的不可变调整事件、证据和审批流程。

浏览器只访问计费 Web 同源 `/api/*`；Web 服务将其代理到 Go 私有 `/v1/admin/billing/*`，由 Go 验证会话、角色、CSRF、Origin 和请求幂等性。登录由 Go 针对计费后台主机名签发 host-only Cookie，代理保留受信的原始 Host/协议并阻止伪造转发头，不能把 Go 内网地址写进 Cookie Domain 或浏览器跳转。接口至少包括 `session/login/logout`、`overview`、`users/{id}/wallet`、`orders/{id}`、`refunds/{id}`、`usage/{requestId}`、`reconciliation`、`prices/versions`、`reports`、`audit`。Go 管理 API 不直接暴露公网，代理只允许固定上游和路径、限制请求大小与超时，不接受任意目标 URL。查询支持服务端筛选、游标分页和账期；写操作按领域分成预览与提交，复用 `internal/payments`、`internal/metering` 的事务与现有 Worker，禁止前端直接写账本表。业务表、账号与审计留在 MaterialsX PostgreSQL；LiteLLM 专用库不存 MX 点余额。接口合同先落在 `packages/contracts`，再接前端类型与页面。

### 6.3 计费 Web 独立交付与运维

`apps/billing-admin/` 单独执行类型检查与生产构建，输出带版本标识和校验和的 `dist/billing-admin/`；`runtime/billing-admin/` 保存非仓库配置、访问日志和只读的 Go 私网地址，不保存支付或供应商密钥。提供独立的启动/停止/重启脚本及生产服务单元，暴露 `/healthz`，由 HTTPS 反向代理将独立主机名转发给该进程。其发布流水线只替换计费 Web 产物，并保留上一版本用于回滚；不触发 Go 数据库迁移、不覆盖 LiteLLM 配置，也不重启 `/ops`。反向代理、进程管理和日志保留规则须与部署环境一同交付。

验收时分别停止计费 Web、LiteLLM 和 Go：计费 Web 停止时桌面支付回调、钱包和模型调用仍由 Go 处理；LiteLLM 停止时计费后台仍可查询历史账本并显示代理故障；Go 停止时计费 Web 应明确显示服务不可用且不伪造财务数据。分别重启/回滚计费 Web 与 LiteLLM，不影响另一方进程 PID、版本或配置文件。生产可先同机隔离进程，后续迁移到不同主机只修改私网地址与 DNS，不改变计费域逻辑。

### 6.4 `/ops` 与 LiteLLM Admin UI 的职责

`/ops` 保留“模型采购与路由”工作台：供应商 HTTPS Base URL、协议、密钥引用、四路真实 ID、探针、并发/限流、健康、日志脱敏、代理重启、路由配置发布与回滚。密钥轮换只通过服务端私有存储一次性写入，随后仅显示掩码和时间；请求不能带任意目标 URL。LiteLLM `/ui` 仅供内网服务维护人员查看代理模型、虚拟 Key 和花费日志；不能从该 UI 绕过 MaterialsX 的定价/路由版本发布。

计费后台拥有销售价格草稿、采购/汇率证据和财务审批；`/ops` 拥有代理实际路由部署。统一发布工作流为：核对第 5.3 节快照 → 四路探针 → 审批销售价格与路由版本 → 生成不可变联合快照 → 部署并健康复查 LiteLLM → Go 在一个受控激活记录中启用对应模型+价格版本。失败则回滚代理配置且不激活新价格；已发起请求仍按启动时锁定的旧快照结算。两后台展示同一个发布 ID 和审计链，不提供相互矛盾的可写价格入口。

## 8. 0.3 发布门槛

- 四个公开槽位逐一记录供应商真实模型 ID、可用性、协议、能力及采购价；未通过者保持隐藏或标“暂不可用”，发布说明准确列出实际可用数。
- ¥10/50/100/500 四档订单金额与 100/500/1000/5000 MX 点严格对应；有效回调重放、乱序、超时查单只到账一次。退款后账本仍能从流水重建。
- 四种模型均通过真实流式、工具往返和最终 usage 验证；输入/输出/缓存分类准确。缺失或不可信 usage 不自动放款、不自动重试生成，进入待核对。
- 新旧积分钱包隔离；并发请求不能透支。新价格和汇率发布不改变旧任务账单，运营端能追溯每笔收入/采购成本依据。
- 独立计费后台主机名与现有 `/ops` 均可使用、互有清晰入口且权限隔离；计费后台按第 6 节完成总览、用户、充值、消费、退款、对账、定价、报表与审计，品牌使用 MaterialsX 海军蓝/青色。参考后台的信息层级可辨，但无小力品牌资源或业务数据。
- 计费后台不同角色的读写权限由 Go API 拒绝越权；计费后台使用 host-only 独立 Cookie，`/ops` 继续限制在其路径，跨主机 CSRF/Origin 与幂等/版本检查生效。报表的实收、未消费点数负债、已消费收入、供应商成本和未知项分别展示，不能把充值直接记作模型毛利；现金/点数/供应商三账可逐笔追溯。
- Go、计费 Web、LiteLLM 有三个可分别部署的产物/版本、运行目录、服务单元、健康检查、日志与回滚流程。分别杀死与恢复三个进程，核验故障隔离：计费 Web 故障不影响桌面收费调用，LiteLLM 故障不影响历史账本查询，Go 故障时计费 Web 显示不可用；重启不重复扣点或重发未知终态请求。
- LiteLLM 只监听私网、计费 Web 不直连其管理 API；桌面安装包/日志/数据库导出不含四个供应商 Key。计费 Web 仅代理固定的私有 Go 管理 API，不持有业务数据库凭据或资金规则。
- LiteLLM 专用数据库与 MaterialsX 业务数据库分权；本机与生产均验证专用角色非超级用户，数据库迁移、备份/恢复及 `/ui` 管理功能在无 Docker 部署下可重复运行。
- PostgreSQL 备份/恢复、配置回滚、密钥轮换、支付与供应商对账、告警处置均有可重复操作记录；macOS arm64 与 Windows x64 完成各自桌面回归。
- 执行 `npm run check`、`npm test`、`npm run control-plane:test`、计费后台类型检查与生产构建、0.3 专项集成测试；记录真实供应商调用和小额实付的脱敏验收结果。未通过这些门槛时仅发布受限预览，不开放四模型正式收费。

## 9. 技术依据

- LiteLLM 官方 [Admin UI Quickstart](https://docs.litellm.ai/docs/proxy/docker_quick_start)、[生产部署](https://docs.litellm.ai/docs/proxy/deploy)及[虚拟 Key 文档](https://docs.litellm.ai/docs/proxy/virtual_keys)：自带 `/ui`，模型管理、虚拟 Key 和花费记录依赖 PostgreSQL；官方 Quickstart 以 Docker 为例，本项目须另外验收无 Docker venv 安装是否完整提供 UI 与数据库迁移能力。
- LiteLLM [自定义输入/输出单价](https://docs.litellm.ai/docs/routing)、[成本追踪](https://docs.litellm.ai/docs/proxy/cost_tracking)和[价格字段 Schema](https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.schema.json)：模板按单 Token 写入标准档采购价；缓存及长上下文必须与锁定版本和供应商账单对齐。
- LiteLLM [安全配置](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10)：内容日志脱敏需显式配置。
