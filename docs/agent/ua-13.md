# UA.13 团队研究与远程 MOOS

日期：2026-10-06。状态：工程预览；公网生产部署与真实上游纠错资格单列，不能以本机测试替代。

## 使用入口

桌面端「研究数据与交付 → 团队研究」，中英文切换和全局主题沿用原研究页。

1. 在云服务中心登录现有 M5 账户。项目所有者按账户 ID 授权成员，购买订阅和 M5 管理员身份不会自动得到项目数据权限。
2. 点击「查看我的共享项目」，选择并连接。一个本机工作区绑定一个共享项目。
3. 编辑者共享材料体系、研究条件、备注与当前选定的 MOOS 引用。成员可以导入到本机研究：逐条重新读取真实来源及证据，复用原研究快照、条件、分析和交付流程；不从服务器下载本机项目文件。
4. 使用本地模型和 Pi 或 Codex 原执行循环，调用原 `research_data`、科学方法、质量检查与交付工具。共享项目只允许本地模型；任务授权移除外部网络、任意终端操作。固定后端仍可读取授权 MOOS 服务和执行本地分析。账户、角色、项目范围或连接版本变化时隔离旧引擎上下文；任务冻结授权摘要，不能静默替换。研究结论仍需科学复核。
5. 编辑者提交原值、字段路径、新值、证据 ID 和原因；审核者独立批准或驳回，作者不能审核自己的提议，即使后来角色发生变化。
6. 已批准的提议可导出实际 JSON 回写包，使用 MOOS 正式导入与审核流程更新原数据。审核者再粘贴 MOOS 返回的真实新版本引用，系统核验版本、审核状态、包哈希、投影哈希、目标行 ID、修正值与证据后才标记「MOOS 新版本已核验」。

关闭连接保留授权绑定，防止含团队数据的工作区回退到本机 MOOS 或切换云模型。要使用非团队云任务，应创建独立工作区。已授权用户原先导出的文件不能靠后续撤权自动召回；本机快照保留供审计，撤权后应用界面与后续来源调用拒绝使用。

## 同一套实现

- `packages/contracts/src/team-research.ts`：成员、共享清单、纠错、版本与桌面合同。
- `packages/agent/src/team/`：项目 ACL、审计元数据、原 M5 验证、源投影、审核、Streamable HTTP 服务。
- 原 `MaterialsMcpClient` 同时支持 stdio/HTTP；原 `DataSourceRouter` 按本机项目选择客户端并核对 `project-research` 项目证明。没有第二套 Agent 循环。
- `apps/desktop/main/team-research.ts`：主进程专用的同源 M5 凭据传输、授权检查、本机导入与回写包文件。
- 原 M5 账户、PKCE、安全存储、刷新和设备撤销保持唯一身份来源。团队数据库仅存项目授权、共享条件、提议和操作哈希，不保存账户密码、Token 或整份 MOOS 数据库。
- 删除了 `ResearchService.configure` 中为了重建 MCP 连接而创建一整套无人使用的科研服务对象的冗余路径。

## 授权和传输边界

正式入口使用现有 M5 HTTPS 同一域名 `/v1/research/...`。主进程的 `researchRequest` 只接受严格白名单路径，不把 M5 Token 发给另一个自定义 MCP 域名，不跟随跳转，不自动重放结果未知的 POST。

每次请求验证 M5 `/health` 的生产标记、`/v1/me` 的账户状态与设备；服务端再验证项目角色和精确的 sourceId/experimentId 范围。异步读取完成及修改提交前重新核对身份和授权版本。角色修改和撤销使用版本冲突检查，客户端声明 `X-User-ID`、`X-Reviewer-ID` 等身份头不被接受。

共享范围由运维人员在服务端建立，项目所有者只能在已批准的范围内授权成员，不能以订阅或项目角色扩大源数据范围。原 MOOS MCP 与后台继续位于服务器本机，不直接暴露只读后台给公网。

资产、分页游标和大记录资源使用随机 `moos-team://...` 句柄，绑定账户、项目、当前授权摘要和 10 分钟有效期。每次读取重新验证底层来源版本与权利，原始图片导出未开放，仅预览。全局搜索只返回授权记录，不返回全库数量、原始全局回执或路径；游标不展示上游游标。HTTP 请求体、并发、资源大小和读取时间均有界限。

严格检查 Host/Origin，拒绝错误协议版本；GET/DELETE MCP 返回 405，不建立额外会话。正式服务要求 TLS 或显式声明的 loopback TLS 反向代理；开发身份不能通过生产标记检查。[MCP Streamable HTTP 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

用户项目操作审计复用 M5 的真实 actor ID；服务端初始化和数据范围配置明确记录为 local-operator；授权、读取、拒绝、提议、独立审核、导出和上游核验写入项目操作日志。原身份服务继续负责登录、设备和账户审计，不伪造 M5 的全局审计事件。项目日志保留操作哈希与最少元数据，不将凭据、配方全文或查询文本写入公开日志。

## 纠错边界

本轮没有找到可授权调用的统一 MOOS canonical 纠错写 API。现有图片反馈接口声明 `local_feedback_only_no_canonical_change`，不能充当真实上游写入。

因此：工程闭环是「提议 → 独立审核 → 导出回写包 → 授权 MOOS 导入/审核 → 新版本实证核验」。MaterialsX 不修改 MOOS 数据库、不猜测写接口、不伪造审核身份。`approved-awaiting-upstream` 与 `applied` 明确分开；回写包固定 `canonicalWritePerformed:false`。

新值当前只支持标量，目标限定 observations/recipes/ingredients/processes/nodes 的已有字段；不支持删除实验、变更成员以外的原始库权限、任意 JSON Patch 或整包覆盖。新版本须保留目标行 ID 和证据 ID；重排目标行或更换证据需重新提出有证据的纠错，不能模糊匹配猜测目标。

## 服务启动

Node 24.7+，已有 MOOS MCP 已构建。服务端无需安装 Codex，也不运行 LLM。

```bash
npm ci
npm run build:core
# 使用本机私有配置；变量名见 .env.example。不要提交配置或数据。
npm run ua13:team -- init /absolute/private/team-project.json
npm run ua13:team
```

私有初始化文件示例（账户 ID 必须来自现有 M5 账户，示例 ID 为占位）：

```json
{
  "name": "PVDF 团队研究",
  "ownerId": "existing-m5-account-id",
  "description": "已授权的数据范围",
  "scopes": [{"sourceId": 1, "experimentId": 1}]
}
```

`init` 仅创建元数据，不读取 MOOS 或创建用户。服务端运维更新数据范围使用 `npm run ua13:team -- scopes /absolute/private/scope-change.json`，文件提供 projectId、expectedRevision、scopes 和至少 5 字的 reason；记录为明确的 local-operator 操作并提高项目版本，立即使原句柄失效。桌面所有者不能调用这项运维入口。输出共享项目 UUID，所有者在桌面端连接后添加成员。生产账户数据不能由开发账户冒用。

生产建议：M5 和团队服务共用一个 HTTPS 网关；分别转发 `/v1/research/` 与原 M5 路由。团队服务监听 `127.0.0.1:8793`，仅可信同机代理可转发。模板见 [部署示例](../deployment/ua13/README.md)。开发测试如需共用本机入口，也由同一个 loopback 反向代理分流，不把团队服务冒充 M5 身份服务。
