# MaterialsX 0.3：1000 人并发容量初估

日期：2026-10-07。这里的“1000 人并发”必须分成**1000 人同时在线**与**1000 路模型请求同时生成**。以下为规划量级，并非压测结果或供应商承诺。0.3 当前是本地单机诊断配置，不能承诺任一生产场景。

## 现配置的硬上限

- LiteLLM 每个三模型部署的 `max_parallel_requests: 2`，单代理进程最多约 6 路同时调用；超限请求会立即得到 429，且该值按进程计算，不在副本间共享。见 [LiteLLM 路由文档](https://docs.litellm.ai/docs/routing)。
- Go 网关默认 `MaxConcurrent: 8`，且本地 0.3 模型仅支持 `alpha-test` 诊断路径；MX 点真实计费没有接入该路径。
- 当前只有单机 Go、LiteLLM、计费 Web 与本地 PostgreSQL，没有多节点共享限流、故障切换、生产 HTTPS 或供应商吞吐额度证明。

## 按请求形状估算

以每次调用平均占用连接 30 秒、输入 2000 Token、输出 500 Token 为假设。Little 定律近似为 `请求/秒 = 同时生成路数 ÷ 30`。若 1000 人在线，其中 5% 同时生成，则是 50 路、约 1.7 RPS；10% 同时生成是 100 路、约 3.3 RPS。若**全部 1000 人同时生成**，则约 33 RPS，供应商需提供至少 1000 路并发，并能承受约 400 万输入 TPM 与 100 万输出 TPM。真实长会话、工具调用、缓存与重试会改变这些数值。2026-10-07 一次极短的 Claude 探针也出现 6755 个供应商计费输入 Token，说明不能只用客户端提示词长度估算预留额或供应商 TPM；必须用实际终态用量标定输入放大系数。

| 目标 | 初始计算资源建议 | 前提与验收 |
| --- | --- | --- |
| 1000 人在线，50–100 路同时生成 | Go API 2 副本，每副本 4 vCPU / 8 GiB；LiteLLM 2 副本，每副本 4 vCPU / 8 GiB；独立计费 Web 2 副本，每副本 2 vCPU / 4 GiB；PostgreSQL 主库 4 vCPU / 16 GiB、可靠磁盘；Redis 2 vCPU / 4 GiB；外加负载均衡、备份与监控。 | 供应商每路实际并发与 TPM/RPM 限额先核定；调整按模型分组的限流；采用连接池；用真实 30–120 秒流式负载测试 P95 延迟、错误率、账本一致性。 |
| 1000 路模型同时生成 | 先以 6–12 个 Go 副本和 6–12 个 LiteLLM 副本（各 4–8 vCPU / 8–16 GiB）作为压测起点；PostgreSQL 至少 8 vCPU / 32 GiB，独立 Redis 与连接池。**不能直接按此采购并宣称足够。** | 必须先取得供应商的 1000 路/约 500 万 TPM 总额度、分模型额度和故障行为；把代理每路并发上限与 Go 全局上限按实际配额联合设定；完成阶梯压测后再定副本数。 |

LiteLLM 官方[生产部署指南](https://docs.litellm.ai/docs/proxy/deploy)建议无状态代理至少双副本、PostgreSQL 与 Redis，并提醒数据库连接池按 worker/副本叠加；副本数不能仅按 CPU 扩张。基于这个限制，账本 PostgreSQL 要用连接池和事务指标做容量验收，避免高峰时连接数先于 CPU 耗尽。生产流式响应主要占用网络连接与供应商容量，不能只用本机 CPU 利用率推断可支持人数。

## 正式承诺前的测试门槛

在隔离环境先做 10、50、100、250、500、1000 路持续流式阶梯压测；逐级核对用户余额预留、终态 usage、供应商账单、取消/超时/重复回调、退款、服务重启后的幂等性。将并发、RPM、TPM 和成本按模型分别度量；任何无法确认 Token 分类或供应商扣费的请求保持待对账，不自动把缺失量当零。只有完成真实 MX 点结算集成、联合激活、供应商配额确认、生产故障演练后，才能给出正式容量承诺。
